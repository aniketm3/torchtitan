Reproducing the small-scale half of Aleph Alpha's hierarchical sweep: estimate the ceiling, sweep activation checkpointing × batch size, then profile to find what's left. Phases 0 to 2 on one H100, then Phase 3 on four H200s.

What it showed

Memory is predictable. Every mode has the same ~31 GiB fixed cost (25.6 GiB of weights and optimizer state, plus ~5 GiB of CUDA context and workspaces), leaving ~48 GiB for activations. Max LBS ≈ 48 GiB ÷ memory per sequence: 5.8, 9.6 and 56, against 4, 8 and 48 measured.

Bigger batches are faster, until the GPU is saturated. 18–19k tok/s at LBS 1 rises to 29–31k. Full-AC flattens past LBS 16 and doesn't improve as it fills memory.

Full-AC looked only ~10% slower than none at the same LBS, although it redoes 29% more matmul work. That puzzle sent us to the profiler.

Root cause: a sync on every step

Logging calls loss.item() and grad_norm.item() (torchtitan/trainer.py ~450–462). To return a Python number, the CPU must wait for the GPU to finish all queued work: a 684 ms cudaStreamSynchronize in the trace. The GPU's queue is then empty. It sits idle while the CPU stages the next batch (aten::view 56 ms, host-to-device copy 43 ms, aten::reshape 42 ms), roughly 150 ms per step. With log_freq=1 this happened every step.

Fix: log every 10 steps (Phase 2b, same machine)

Nine of ten steps now return at trainer.py ~410 before any .item(), so the CPU runs ahead and stages batch N+1 while the GPU computes step N. Result: 30,577 → 42,346 tok/s (+38%), step 1.07 s → 0.77 s, GPU busy 98.8%. With idle time gone, full-AC is −15% at LBS 8 and −12% at LBS 24: selective wins, outside noise.

Where the GPU's time goes now (735 ms of kernels)

From trace_summary.py. Matmuls run at about 777 TFLOPS while active (79% of peak), so they're already efficient. The remaining headroom is the ~41% that isn't matmul, starting with RMSNorm (one unfused eager kernel, forward plus backward).

Why small batches are inefficient (the "worst" trace, LBS 1): the optimizer costs 23.5 ms per step whatever the batch size. At LBS 1 that's 15% of GPU time; at LBS 8, 3%. Matmuls are only 38% of kernel time at LBS 1. With few tokens per step, fixed per-step costs dominate.

Phase 3 · 4× H200 · dense done, MoE cut short

Many GPUs: who holds what, and what moves

One GPU only had to be kept busy. With several, each step also has to move data between GPUs, and the question becomes whether that movement hides behind compute or makes the GPUs wait. 8-GPU machines were sold out, so this ran on one 4× H200 node. All four GPUs share NVLink, about 450 GB/s each way.

What the traces show (rank 0, step 19)

FSDP: the compute stream is 99.5% busy over a 747 ms step. Meanwhile, on separate streams, ncclDevKernel_AllGather (~100 ms per step) and ReduceScatter (~125 ms per step) run alongside it. That's ~30% of the step spent communicating, almost all of it hidden. DDP shows the same picture with one kernel, AllReduce, at ~200 ms per step. The kernel names end in f32: gradients are averaged in fp32, so twice the bytes of bf16. The 2–6% that is lost is mostly compute and communication sharing the GPU, not idle time.

Part B: Qwen3-30B-A3B, a mixture of experts

30.5 B parameters, but each token only uses 3.0 B: 8 of 128 experts per layer, plus attention. 29 B of the parameters are experts. Compute scales with the 3 B active; memory and FSDP traffic scale with all 30.5 B. Under FSDP=4, each GPU holds 113.7 GiB of the 139.8 GiB just for weights, grads and optimizer, so only full AC at a small batch fits.

What to look for in the multi-GPU traces

  1. A second busy GPU stream full of ncclDevKernel_AllGather, ReduceScatter, AllReduce, or SendRecv (all-to-all) kernels.
  2. Overlapped communication: NCCL kernels run while the compute stream is also busy. That's free.
  3. Exposed communication: the compute stream is empty while an NCCL kernel runs. That time is lost; expect it in the MoE LBS 1 trace.
  4. FSDP prefetch: the all-gather for layer N+1 starts while layer N computes.

This is the "compute-bound vs communication-bound" check the blog ran at each scale.

Self-check

What you should be able to explain

How are tokens/s, MFU and memory % measured, and why optimize tokens/s?
tokens/s/GPU = tokens since the last log ÷ elapsed time ÷ GPUs. MFU = tokens/s × FLOPs per token (13.14 G) ÷ peak (989 T). Memory = peak reserved ÷ total, because reserved is what decides OOM. Tokens/s directly sets time-to-train for a fixed token budget. MFU depends on how you count FLOPs (causal attention, recompute), so it's harder to compare across teams.metrics.py ~540–570
Where does GPU memory go, and why does it cap batch size?
A fixed 16 B/param (fp32 weights, grads and two Adam moments) = 25.6 GiB, plus ~5 GiB of runtime overhead. Activations grow linearly with LBS: 8.3 / 5.0 / 0.85 GiB per sequence for none / selective / full. Max LBS ≈ free memory ÷ per-sequence cost.Phase 1 table; memory_viz snapshot
What's the activation checkpointing trade-off, and why does selective usually win?
AC stores less during forward and recomputes the rest during backward: memory for compute. Selective recomputes only cheap elementwise ops (norms, SiLU, RoPE), cutting ~40% of activation memory for almost no extra matmul work. Full cuts ~90% but reruns every block's forward pass (+29% matmul time here), and the bigger batches it allows didn't win that back: −12 to −15% after the fix.activation_remat.py; Phase 2b table
Why does throughput peak near full memory, and what happens past it?
Bigger batches amortize fixed per-step costs (optimizer, launches) and give the GPU larger, more efficient kernels. For a mode still climbing when memory runs out, the best point is the largest batch that fits (selective LBS 8, 91%). Past ~95%, LBS 9 at 97% ran 5% slower despite 12.5% more tokens per step, consistent with the blog. We saw no logged allocator retries, so the mechanism is unconfirmed.Phase 1 curve; Phase 2 LBS 9 run
How do you read a trace and show a run is compute-bound?
Measure GPU busy % (the share of the step with a kernel running) and look at what fills the gaps. Idle stretches with the CPU busy above them mean host-bound: a sync, launch overhead, or data staging. Compute-bound means ~99% busy with matmuls dominating kernel time and running near peak. After the fix: 98.8% busy, matmuls 59% of kernel time at ~79% of peak.trace_summary.py; Perfetto steps above
